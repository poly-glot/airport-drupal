# Build brief — Drupal Canvas port (the contract every agent works from)

Read in this order: this file, `docs/drupal-canvas.md` (the plan), `docs/design/spec.md` (normative design law), `docs/status.md` (what is open). The catalogue `docs/design/system.md` is reference, subordinate to the spec. `docs/brief.md` is the original delivery brief; §2.1 describes every homepage element and §2.1.3 the hero sky variants.

`static/` is the contract. Markup, class names, text, link targets, ARIA and the DOM order come from it unchanged. The port passes when `scripts/compare_port.py` diffs clean against the Drupal site.

## Repo layout

```
static/                                   contract, read-only
scripts/                                  build_seed.py (gains --target canvas), compare_port.py, hero_contrast.py
docs/                                     this brief, delivery brief, plan, design spec, status, copy deck, imagery register, canvas-reference.md, platform.md
drupal/                                   composer project root (composer.json, web/, recipes/, config/sync/, seed/, Dockerfile, canvas.config.json)
drupal/web/themes/custom/meridian/        the theme: components/, css/base/, templates/; static assets are served from the web/assets symlink
drupal/seed/{pages,regions,content}/      generated by build_seed.py, never hand-edited
.claude/                                  CLAUDE.md, skills/, agents/ for whoever picks this up later
```

Theme machine name `meridian`. Theme regions: `notice`, `header`, `content`, `footer`. The only base library is `meridian/base` (fonts, tokens, base, layout, utilities). There is no shared JS helper library: a component inlines the helpers it uses. Do not add to `css/base/`; tokens are closed.

## One component = one directory

`drupal/web/themes/custom/meridian/components/<name>/` holds exactly:

| File | Rule |
|---|---|
| `<name>.component.yml` | metadata, props, slots, `libraryOverrides` when the component has JS |
| `<name>.twig` | markup copied from the static element; every static class name kept; root element carries `{{ attributes }}` |
| `<name>.css` | the matching file from `static/assets/css/components/` copied verbatim (or the relevant rules split out of `content.css`); no new hex, no new selectors unless the static CSS had them |
| `<name>.js` | only if the static `site.js` has an `enhance*` for it (see JS section) |
| `README.md` | derivation: which static file and element it comes from (path + a distinctive class or heading), which spec rule governs it, props and slots in one table, known deviations (should be none) |

Machine names and props are the ones in `docs/drupal-canvas.md` §4. If the static markup forces a change, change the plan table too and say so in the README.

### component.yml shape

```yaml
$schema: https://git.drupalcode.org/project/drupal/-/raw/HEAD/core/assets/schemas/v1/metadata.schema.json
name: Help item
status: stable
group: Meridian · Inner pages
description: One ruled row with icon, title and body, as on the homepage help band.
props:
  type: object
  required: [title]
  properties:
    icon:
      type: string
      title: Icon
      enum: [assistance, children, first-flight, alerts, lost-property, contact]
      examples: [assistance]
    title:
      type: string
      title: Title
      examples: [Special assistance]
    body:
      type: string
      title: Body
      examples: [Book help through the terminal at least 48 hours before you fly.]
    href:
      type: string
      format: uri-reference
      title: Link
      examples: [/help/special-assistance/]
slots:
  items:
    title: Items
    description: Help items, one per row.
libraryOverrides:
  dependencies:
    - core/components.meridian--section-head
```

Rules:
- A slot whose children are all one component declares it: `expected: [meridian:<child>]` (help-list does). Canvas 1.12 does not enforce it yet; the declaration is the configuration the enforcement will read.
- Every prop has `title` and at least one `examples` value taken from the static site. Canvas builds the sidebar preview from the first example. The `title` is what an editor sees in the Settings panel, and Canvas has no in-place text editing, so it must name the text as it sits on the page: `Section heading`, `Line under the heading`, `Link text on the right`, `Bold start of the note`. Never `Title`, `Label`, `Body` or `Text`.
- Prop types: `string`, `integer`, `boolean`, `string` + `enum`, `string` + `format: uri-reference` for links, and images as `$ref: json-schema-definitions://canvas.module/image`. No `array`, no `object` props: a collection is a slot holding child components. Formatted text (prose, table bodies) is a `string` prop with `contentMediaType: text/html`.
- Groups: `Meridian · Bands` (homepage sections), `Meridian · Inner pages`, `Meridian · Parts` (small leaves like fact, wait-chip, status), `Meridian · Chrome` (header, footer, notice bar).
- Slots are Twig blocks: `{% block items %}{% endblock %}`. A container renders nothing else inside the slot.
- Images: props of the image type are rendered through `{{ include('meridian:picture', { image: image, sizes: '...', loading: 'lazy' }, with_context = false) }}`. `picture` takes the static slot stem convention: `image.src` holds the stem (for example `/assets/img/airport/shopping-hero`) and the component emits `<picture>` with AVIF, WebP and JPEG sources exactly as the static markup does (check a static page for the exact `srcset`/`sizes` pattern before writing it).
- Icons: inline SVG copied from the static markup, selected by the enum value with a Twig `{% if %}` chain or a map; `currentColor`, no emoji.

### Twig rules

- Copy the static element's markup. Replace text with props, repeated children with a slot. Keep the exact element nesting, class names, `aria-*`, `id`s, `hidden`, `data-*` (the board has 218 `data-flap` cells; keep them).
- Root element: `<section class="band city-rail"{{ attributes }}>` style, attributes last. Canvas and Drupal add their own attributes there.
- No comments in Twig, CSS or JS. Explanation lives in the README.
- Headings: a `heading_level` enum prop (`h2`, `h3`) where the static site varies the level, rendered as `<{{ heading_level }}>`.

### JS rules

- One behaviour per component, Drupal style, using `once` so Canvas previews and BigPipe do not double-bind:

```js
(function (Drupal, once) {
    function enhanceCityRail(rail) {
        ...the static function, verbatim, with Meridian.wrapIndex etc. for shared helpers...
    }

    Drupal.behaviors.meridianCityRail = {
        attach(context) {
            once('meridian-city-rail', '.city-rail', context).forEach(enhanceCityRail);
        },
    };
})(Drupal, once);
```

- `libraryOverrides` for a component with JS: `dependencies: [core/drupal, core/once]` and `js: { <name>.js: { attributes: { defer: true } } }`.
- The function bodies come from `static/assets/js/site.js` unchanged. Ownership: `enhanceMenu` → site-header; `enhanceNotices` → notice-bar; `enhanceHeroSky` and its SKY_* constants → hero; `enhanceTabs` → tabs; `enhanceBoardSearch`, `enhanceSplitFlap`, `enhanceStatusTips`, `advanceClock`, the FLAP_* constants and the whole flap engine, `BOARD_EVENTS` → flight-board as `board-events.json`, fetched by the behaviour; `enhanceCityRail`, `fullyVisibleRange` → city-rail.

### Design law (spec §3, §4, §5, §11) is enforced by grep

Before you finish, run from the repo root and fix anything it prints:

```bash
python3 scripts/design_battery.py
```

It first runs `scripts/sync_static.py --check`, which fails if any theme CSS or JS differs from what `static/` generates or exists without being generated; then it checks every component directory: no comments in Twig or metadata, no raw hex in Twig, every prop has a title, examples and a scalar type, and a README exists. It prints nothing but `design battery ok` when clean.


## Content and data boundaries

- Editorial text lives in Canvas pages (seeded from `static/`), never hard-coded in Twig. The only literal text allowed in Twig is UI chrome the static site hard-codes everywhere (for example "Skip to main content", legend labels, "Updated" prefixes) and SVG `<title>`s.
- Data the brief calls entities (notices, flights, car parks, airlines, routes, destinations, offers, facilities, FAQs, roles, releases, help items, towers) will come from content types and Views. A component that renders such a list exposes a slot; the Views row template will call the leaf component. Do not build Views in this phase unless your assignment says so.
- Forms (`form` kind enum), terminal maps and the site map are code-owned Twig: copy the static markup for each kind; they are functionality, not content.

## Self-check before reporting

1. `python3 scripts/design_battery.py` prints `design battery ok`.
2. For each component, render-compare by eye: open the static page in the browser or `sed -n` the static element and your Twig side by side; every class and attribute present.
3. README written for each component.
4. Report: list of components written, any plan deviations, anything you could not derive from `static/` (stop and report rather than invent).

Commit nothing. The coordinator commits.
